## Choices the records do not cover (to confirm)

1. **R1 at publication, not finalize.** The coordinator asked for the finalize gate back for
   non-system export-only jobs. Under the 2026-09-25 quota record a transient candidate is
   uncharged and publication gates the net growth, and C5 removed the finalize gate for every
   job; a finalize gate would check the candidate's gross bytes. The publication gate now fires
   (the candidate term that cancelled it is gone), which is what the test asserts. Say if the
   finalize gate is wanted as well.
2. **Text uses the same model.** A text source's NULL state is seed(base) too (seeded under
   Yjs client 0 so every instance agrees), its baseline is always derived, and the generated
   `storage_bytes` rule applies to every row, so text is charged pending effects plus growth
   beyond its seed instead of state + baseline + effects. The quota record names Office sources.
   Existing text rows keep `seed_bytes = 0` (charged in full) because their seed size is unknown;
   0033 only NULLs their baselines.
3. **Captured-state reader.** The plan says `COALESCE(c.state, d.state)`; with NULL source
   states that confuses "not copied yet" with "captured seed(base)" (a save after capturing a
   NULL state would make COALESCE read the new state). Readers use
   `CASE WHEN c.checkpoint=d.checkpoint THEN d.state ELSE c.state END` instead.
4. **Candidate seed.** Resolved in the follow-up below: candidates keep only `seed_bytes`.
5. **Fonts.** The CJK add-on (33 MB) is not shipped: CJK text keeps browser fonts, and the provider
   never requests CJK faces, so a missing CJK face is not reported as an error. PPTX keeps its
   four Liberation Sans faces as `Arial`; loading the full metric-compatible set for PPTX would
   fetch about 7.4 MB on a first open, and the PPTX engine takes its font list up front. A
   last-resort face registers under the requested (document) family name so paint matches
   measurement.
6. **Roots check refusals.** An update that refers to content neither the room nor the update
   holds is refused as well (it could not be classified).
7. **XLSX save button.** XLSX has no `onSaveRequest`; its toolbar save still serializes and the
   bytes are discarded (Ctrl/Cmd+S is captured by the runtime host, as before).
8. **Unbound SHA drafts.** A never-parsed upload has no source SHA until its first save binds it
   (before, the first open bound it). Drafts written before that carry an empty SHA, so after a
   reopen they read as another lineage (recovery prompt, not a merge). Rare and safe.
9. **Pause and first saves.** With no seeding write left, the pause has nothing to refuse there;
   a first save of an open room lands like any flush.

## Follow-up: opening charges the source alone

The C6 journeys found a first open charged 2 bytes: the generated column counted the empty effect
list `[]`. Now `[]` counts 0, so a source is charged exactly its bytes until something changes.
`0033_office_storage_rule.sql` (edited in place) uses

## Follow-up: no whole room as one update to an engine

The fork (`094d1ebe`, in `capy/upstream-merge` `1ca0968b`; `vendor/betteroffice` stays at
`e912e8e0` until the coordinator bumps it) caps only incoming updates at 64 MiB; a stored state
loads uncapped. After `collaboration-ready` the host used to send its whole doc back to the runtime
as one update, so a DOCX or PPTX room over 64 MiB still could not open. It now sends only what the
replica lacks, the diff against the state vector of the state the replica reported
(`replicaCatchUp`, `src/features/files/useOfficeRuntime.ts:39-49`, used at `:377-378`). Test:
`src/features/files/officeProtocol.test.ts:190-205` (a 100 KB room, one later edit: the catch-up is
under 100 bytes and the replica converges).

Swept `src/office-runtime` and `collaboration/src` for other whole-state updates into an engine:

- DOCX loads every stored state through `loadState` (editor `initialUpdate`, the export worker, the
  bundle's `open`, the resident worker), PPTX through `openCollaborativeFromUpdate` or
  `initialUpdate`: the uncapped load path.
- XLSX has no separate load path: the export worker (`src/office-runtime/exportCheckpoint.worker.ts:36`,
  `workbook.applyUpdate(checkpoint)`), the bundle's `open`
  (`vendor/betteroffice/shared/office-checkpoint.ts:952`, `applyUpdateJson`) and the editor's
  `initialUpdate` all go through `apply_update_v1`, and the XLSX engine also caps a stored state
  and its encoding at 64 MiB (`validate_collaboration_size`, `validate_collaboration_state` in
  `crates/betteroffice-xlsx/src/workbook.rs`). Schema 8 states are overrides only, so this needs a
  very large edit history; lifting it is fork work.
- The host forwards each of its doc's updates to the runtime one by one. A single large update
  there, such as a provider sync step 2 after a long disconnect in which others added more than
  64 MiB, still arrives as one engine update; that is one real change, not a resend.
