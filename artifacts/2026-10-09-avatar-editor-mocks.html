Avatar editor mocks

Picking a profile photo in onboarding or Settings > Account opens a crop step instead of previewing the file as is. The user drags the photo inside the circle, zooms with the slider, wheel or pinch, and can rotate in 90° steps. The output is always a 512×512 square, drawn round in the app. Every stage below works: drag, scroll, pinch, arrow keys, + and -. Apply, Save and Confirm draw the real 512 px crop into the avatars; Restart puts a screen back.

Open questions for Epo

  1. Rotate: keep the 90° button? Browsers already apply EXIF orientation, so it only fixes sideways scans and screenshots.
  2. Size limit on the pick: the output is always 512 px, so the 10 MB check on the original only guards decode memory. Keep it, raise it (25 MB), or limit pixels instead (about 40 MP)? The upload hint text changes with it.
  3. Apply: keep the crop pending until Save or Confirm, as the photo is today, or store it in Clerk right away?

Recommendation: A with the surface veil. One shared dialog serves both entry points through useProfilePhoto, the stage is large enough to place a face precisely on a phone, and the dialog-over-dialog in onboarding already happens with Choose icon. B squeezes a small stage into a busy row; C's previews repeat what the circle already shows.

Build notes

  • One AvatarEditorDialog: useProfilePhoto opens it after the type check with an object URL, and Apply hands back a 512×512 File from canvas.toBlob, which stays photo.file for the existing Save path to Clerk.
  • Pointer events with capture for drag, two pointers for pinch, wheel and pinch zoom around the pointer, arrow keys move and + / - zoom. The image can never leave part of the circle empty.
  • Decode once with createImageBitmap; the stage moves it with a CSS transform and only Apply draws to a canvas.
