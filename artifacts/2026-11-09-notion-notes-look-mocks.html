On the different BlockSuite bars

Every floating bar is one component (editor-toolbar) fed by a registry: 20 packages register their actions (text, callout, image, link, note card, shape, stroke, highlighter, connector, text element, group, mind map, multi-select, and our plane and chart cards). Restyling that one component restyled all of them at once, as the captures show, and Frame, Comment and the page-mode entries stay removed on the board. That is also the answer to E3: tables, media and embeds all get their bar from the same component.

E1 and E2

E1 · "Why only BlockSuite?"It is both: the note and the canvas are both BlockSuite, and both take the look. The only thing left out is the old Plate note editor, which is deleted at the cut, so restyling it would be thrown away. Say so if you want Plate restyled as well.
E2 · BlockSuite's widgets, restyled (D12), or our own React toolbarsRecommended: keep BlockSuite's (D12 stands). Their bar already knows every selection kind above, positions itself, handles keyboard and touch, and took our look with six small marked patches. Our React toolbars would have to re-implement each of those 20 action sets and the board's, for the same picture. What D12 still owes is its other half: AFFiNE's icons and English strings, to be swapped for Hugeicons and paraglide (question 3).

TTables

The hover handles (⋯ over a column, ⋮ beside a row, + bars at the right and bottom edges) are in both options, since Notion and AFFiNE both have them. The difference is whether a floating toolbar also appears.

T1Handles only (Notion)

  • No toolbar on tables. Everything a row or column needs sits in its handle's menu; cell text gets the text bar like any text.
  • Replaces PE:24's shared table toolbar for the BlockSuite note.
  • Phones: the handles need a tap on a cell first (Notion does the same).

T2Handles and the block toolbar (AFFiNE, PE:24 kept)

  • Two places for the same actions.

PIThe top of the page: title and metadata

Notion: the big title at the top is the page's name, one field: typing there renames the page in the sidebar, breadcrumbs and links, and there is no separate heading block for it. Hovering above it shows "Add icon · Add cover · Add comment". Property rows under the title (Status, Tags, Dates, "+ Add a property") appear only for pages that live in a database; a plain page has none. The top bar shows "Edited 2h ago". AFFiNE: the same: the title is the doc's name (the page block's title text, mirrored into the doc meta), "Add icon" above it, and an "Info" row under it that opens the workspace properties (Tags, Created, Updated, 6 more). Ours today: the material's name sits in the header row with the save status; the note body starts at its first block; the page block's title is stored empty and unused (layout spec).

P1Title in the body = the file's name

  • Notion's and AFFiNE's way: a 40px title the student types into; renaming in the header, the tree or the title changes all three.
  • The header keeps the name for the dropdown and the save status, smaller.
  • Uses the stored page title; the layout spec and the name's save path learn one more source.

P2Name in the header only (today)

  • The body starts at its first block; the first heading is the student's own.
  • Nothing new to store or sync.

I1An Info row under the title

  • Collapsed "Info" line like AFFiNE's; open it shows what we know: Topic, Tags, Created, Updated, Words. Topic and Tags are editable here.
  • The header's status line could go, since Updated lives here.

I2No metadata in the body

  • Topic and tags stay in the file's ⋮ menu and the tree, as now.

What V1 or V2 costs
  1. Bytes: the database and data-view views add 140 KB minified, 28 KB gzipped, on top of the editor's shared code (measured with a throwaway Vite build of the vendored views, with and without them). The note's chunk already imports the database views (getInternalViewExtensions is static), so the build size barely moves; what changes is that their elements register and run.
  2. Store and layout: roomStore.ts refuses affine:database and affine:data-view today; the layout spec (todo-blocksuite-layout.md) needs rows for the database block's columns, cells (a Y.Map per cell per column type), views, filters and sorts, with limits for each.
  3. Converters: the TS and Rust blocks converters (Plate ↔ blocks while both editors exist), the Go materialdoc checks, markdown and the agent's note format (a database exports as a markdown table of its current view), share-page SSR (a static renderer for the table view, no kanban or calendar on the public page).
  4. UI work: the data-view's own toolbar, menus and cell editors take the same token mapping as the rest of the chrome; its date and select pickers are BlockSuite's.
