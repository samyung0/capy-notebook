Why keyed entries merge most simply: a Y.Map merges key by key. Two editors on different elements both keep their work, two on the same element get one of them whole, and nothing has a position, so nothing interleaves or appears twice. The Rust room checks an update by the keys it touched, as it does for table rows today. A Y.Array merges positions: inserts made at the same time interleave, and a move is a delete and an insert, so two moves can leave an element twice. The Rust room would also have to learn to place list entries first.

1 · The model

One element list for every surface. It keeps today's GraphElement as it is, adds the canvas marks as element kinds of their own, and adds a few styles both sides can use. Elements fall into two families:

  • Constructions name their points by id, as quiz graphs do. Dragging a named point moves everything built on it.
  • Free marks hold their own coordinates, as canvas marks do: a stroke, a curve with handles, an ellipse, a formula.

2 · Yjs layout

A quiz figure becomes a map of fields, each replaced whole, with a graph's elements held one by one. Two editors changing different fields or different elements both keep their changes; two changing the same one get the later. A merge that leaves something the validators refuse is repaired on read, never refused.

The same three levels hold a graph on every surface. The quiz entry or the canvas card is a Y.Map of fields. Its elements field is a Y.Map keyed by element id. Each element under it is one plain value, replaced whole. Note figures hold a list of maps today, merged by id; they would move to this layout in a step 4 (D15).

Quiz (step 2)

A chart, plot or graph entry stops being entry.value. Its fields sit on the entry itself, as an image's already do, in both of a quiz's documents (a solution's figures live in the keys document). The writer writes only the fields that changed.

  • A block the dialog can follow. The room entry's key travels with the block to QuestionCard and the dialog, which reads and writes that entry. saveFigure's match by content goes, and with it the second figure a late save leaves today.
  • Live edits (D2). The graph dialog holds no draft. A row writes its element once it parses, coalesced while typing; a dragged point or label writes when the drag ends; a pan or zoom writes the view when it settles. A row that does not parse yet stays local with its error. A new graph joins the question at its first valid change, so opening and closing the dialog adds nothing. Peers with the same dialog open see each element change, and rebaseBlock is not needed here.
  • No stored picture (D16). The graph block drops its image field. Every view draws the graph from its elements with the engine: the quiz editor, attempts, results and share pages. Nothing has to be redrawn or kept in step with the elements. On a share page the Worker's HTML holds a box of the graph's size and the browser draws into it once its script runs; pnpm bench:share-pages is run before and after. An SVG is made only for the note export.
  • A graph's elements are a Y.Map keyed by element id, each element one plain value with an order key, as a table's rows are held (D9). The Rust room already places entries of that shape. The projected block keeps elements as an ordered list, so the validators, rebaseBlock, the bank and every reader of the plain block see no change.
  • Charts go live too (D3). A chart's fields sit on the entry, and its data is held as a quiz table's cells already are: series and labels keyed by id with an order key, one entry per cell. The data pane writes a cell when it is committed, so two editors in different cells both keep their numbers. The projected block keeps its series list. Plots can't be edited in the quiz dialog, so they get their fields on the entry and nothing more.
  • Server writes. Seeding a room from stored questions, the save API and the agent's commands all write blocks through sync_block (quiz.rs); it writes the new shape.
  • Repair on read is new for quizzes, in readBlock and Rust's read_block.
  • Stored rooms. An old plain value would not be refused: it would read as nothing, and the next save would store the question without its figure. UAT quiz rooms are dropped at this deploy and seed again from their stored questions (a room with no Yjs row seeds from its projection). There is no reader for the old shape.

Canvas (step 3)

A plane card is already a Y.Map of its fields. marks is one of those fields and holds a plain list, rewritten whole on every edit. Only that field changes, and nothing changes in how the plane is used. The plane's elements becomes a Y.Map keyed by element id inside its BlockSuite element, each element one plain value with an order key. This is the quiz layout, written by the same writer, which sets only the entries that changed (D10). BlockSuite supports it as it is: the mind map keeps its nodes in a field the same way, watched with @observe, built from plain values by propsToY on create and paste, and carried through snapshots by the surface transformer. A canvas still opens no room. When one is planned, two people drawing on one plane merge element by element with no change to what is stored. The canvas around the card is BlockSuite's own document and is Yjs maps all the way up already (a flat map of blocks, and the surface's map of elements); it is saved whole as one compressed file with its history removed, at most 2 MiB. What a canvas room still needs is on the server: a room that admits BlockSuite documents, which the earlier BlockSuite notes plan described and which was not built. The 256 KiB SVG cap (D11) does not touch the canvas, since a plane card stores no SVG. A list of maps, as first written, would not work: BlockSuite watches a field one level deep.

3 · The engine

A new src/features/graph/ module with no BlockSuite or React dependency:

  • view.ts: the camera (left, top, pixels per unit on x and y), plane↔screen, zoom about a point, pan, fit to elements. tickStep and axisNumber move here. Each surface passes its own zoom range, unchanged: 10⁻¹⁵ to 10¹⁵ pixels per unit for the question editor, 10⁻⁶ to 10⁶ for the plane. Drawing is tested at both ends of each.
  • draw.ts: drawGraph(ctx, frame, view, graph, paper) draws the grid (square or polar), the axes and every element kind with its styles (dash, shade, ticks, arrow, hidden), names and labels. It starts from drawPlane, traceMark, traceFunction and arrowHead, and adds infinite lines, circles, arcs, sectors, angles with their square mark, polygons, hatch marks and wrapped labels.
  • svg.ts: a recorder that takes the Canvas 2D calls draw.ts makes (paths, arcs, Béziers, text, clip, dash, alpha) and writes SVG made only of the tags validGraphSvg allows. graphSvg(graph) is synchronous and needs no container on the page. It measures label text with a canvas, so it runs in a browser; the bank's render script already runs in headless Chromium. Coordinates are rounded to 0.1 px and straight runs thinned. That alone does not keep every SVG under the 256 KiB cap: 100 curved functions on a 1200 px graph, sampled every 2 px, come to about 650 KB by estimate. With no SVG stored anywhere (D11, D16) the cap no longer applies to graphs; an export is a file the user takes away.
  • Formulas in the SVG (D6, step 3). On the canvas a formula keeps drawing as it does now: KaTeX lays it out once, then its glyphs are replayed as text in KaTeX's fonts, its bars as rectangles and its stretched signs (roots, tall brackets) as small pictures. Views of a quiz or note graph draw formulas the same way. An exported SVG (the note export) shows inside an <img>, which loads no fonts, so there the recorder writes each glyph as its outline. A font reader (opentype.js, loaded only when a graph with a formula is exported) takes each shape from KaTeX's own TTF files, 54 KB for the main face and 31 KB for the italic. Bars become <rect>, and stretched signs are copied as the paths KaTeX already holds. The export waits for KaTeX's layout, so it is not synchronous for a graph with a formula. A label-sized formula adds a few KB by estimate.
  • gestures.ts: the plane's gestures for any canvas: the wheel or two-finger scroll pans, pinch and Ctrl/⌘-wheel zoom about the pointer (applied once per frame), the middle button drags to pan, and a settle callback once a gesture ends.

The question editor on the engine

  • Functions are read by functionOf, which the plane uses now, in place of JSXGraph's JessieCode. A test runs both over the allowed function names and the operator cases (-x^2, 2^3^2, implied products) before JSXGraph is removed. Any difference is listed for you, not settled in code.
  • JSXGraph goes (the package, its lazy chunk entry in vite.config.ts and graph.ts's board). The stage is a canvas at the export's pixel size with the toolbar it has now (zoom in, zoom out, Fit, full screen).
  • Rows stay local to GraphEditor. Each keystroke parses one row once and redraws the canvas on the next frame, with no rebuild. The dialog hears the new value in a React transition, so typing never waits on a dialog render. The graph is validated once per change.
  • Points and labels drag as they do now, landing on the view's precision. The bbox reaches the dialog once a gesture settles.
  • Save, the note dialog, graphRedraw and the bank's render script call graphSvg in step 1. Steps 2 and 4 then drop the stored picture (D16) and step 3 drops the bank's file (D11), leaving the note export.

The canvas plane on the engine

boardPlane.ts draws through drawGraph, and boardPlaneEditor.ts takes its wheel, pinch and middle-button pan from gestures.ts. Until step 3 the plane still stores marks; a small adapter turns them into elements when they change, cached on the array, not every frame. Selection, handles, bends, the eraser and the objects list stay in the plane editor.

Implicit curves and inequalities are marked as planned in openwiki/question-bank.md and not built. They are outside this plan; draw.ts draws each kind as its own path, so a kind can be added later.

Risks

  • A new look for stored graphs (D5). Quiz, note and bank graphs take the plane's look everywhere at once, since each is drawn from its elements. The engine's SVG will not match JSXGraph's byte for byte; small offsets in tick numbers and label placement are likely. There is no production data; seeds and fixtures lose their stored pictures.
  • Text width. Labels wrap by canvas measureText while the SVG shows in an <img> with Arial or a fallback. JSXGraph had the same gap.
  • Bank questions already published. Each carries a file address for its graphs; they are rewritten without it when step 3 lands, and the old files stay in the bucket until cleaned up. SVG size now matters only for the note export. Function paths are the bulk; rounding and thinning are tested at 100 functions against the 256 KiB cap.
  • Merge races in step 2. With elements keyed by id (D9) an element cannot appear twice. Two editors reordering at once can give two elements the same order key; read breaks the tie by id.
  • Function values. Our reader and JessieCode may disagree on an edge case; the step 1 test finds it before any stored graph is redrawn.
  • Order of landing. Steps 2 and 3 touch types.ts, BlockDialog.tsx and QuestionCard.tsx, which ui-tweaks-5 is editing; they wait for it to land.
  • UAT quiz rooms. Step 2 drops stored quiz rooms on UAT. They seed again from their stored questions, losing undo history and anything typed in the seconds before the deploy.
  • Room growth from live edits. Every write to a key leaves a small trace in the room's history. Writes are coalesced and no picture is stored; pnpm bench:rates measures what one editor sends before step 2 lands.
  • Share page paint. A graph on a share page draws after the page's script runs instead of arriving in the Worker's HTML. Its box is sized ahead, so nothing shifts. Measured with pnpm bench:share-pages before and after.
  • UAT canvases. Boards saved with marks fail the load check after step 3 (no production data, no shim, per the no-legacy-data rule).

D1 · MODEL

How elements hold their points

  • Two families: constructions name points by id, free marks hold coordinates (the table above).decided 16 Nov
    Existing quiz kinds and validators stay as they are, new kinds are additive, canvas strokes stay one element each. You had no preference, so the simpler merge decided: each object is one entry in the room.
  • Everything by reference: only point holds coordinates; a 30-point curve becomes 31 elements.
    One rule and connected constructions, but the 60 and 500 caps and the number of Y.Maps per stroke grow a lot.
  • Mixed slots: any vertex is a point id or [x, y].
    Canvas marks map one to one, but every layer validates a union per slot and there are two ways to say the same thing.

Others: GeoGebra stores a construction as objects whose commands name their inputs by label (XML reference); Desmos keys expressions by id (API); tldraw and Excalidraw keep free coordinates per shape (tldraw, Excalidraw). Two families is GeoGebra's rule for geometry and the whiteboards' rule for strokes.

D6 · FORMULAS

Formulas in stored SVG

The SVG check allows no <image> or <foreignObject>, and KaTeX's fonts don't load inside an <img>, so a formula can't go into a quiz or note SVG as it is drawn on the canvas.

  • Formulas stay on the canvas until the SVG export can write glyph outlines; quiz and note graphs use labels.
  • Allow formulas in quiz and note graphs, written into the SVG as glyph outlines.decided 16 Nov
    Sharp at any size, and it passes the SVG check as it is. Needs a font reader at save time. The canvas keeps drawing formulas as it does now.
  • As a picture inside the SVG (<image> with a data address).
    The SVG check refuses both in TS, Go and Rust, on purpose. A bitmap blurs when the figure is enlarged or printed, and an SVG picture inside still loads no fonts.
  • As text in KaTeX's fonts.
    An <img> loads no web fonts, so the formula falls back to another font and its spacing breaks.

Others: MathJax's SVG output draws each character as a path, so the picture needs no font files (MathJax docs). GeoGebra Classic's SVG export offers text as editable text or as shapes (manual). Canvas puts equations in as images (equation editor).

How other apps do it

  • Desmos stores state as JSON with expressions keyed by id; asyncScreenshot exports PNG or SVG; no live co-editing of one graph found. API, forum
  • GeoGebra stores a construction as XML of labelled objects and commands; its live client syncs object by object by label, renaming a clashing label to label_1; exportSVG renders the graphics view. Commercial use needs a special licence. Apps API, geogebra-live.js, licence
  • Canvas LMS has no graphing question; Hot Spot clicks on an uploaded image, and equations go in as images. question types, equation editor
  • Google Forms takes images on questions and choices only. update
  • Moodle stores figures as recipes: STACK's [[jsxgraph]] script binding points to inputs, the JSXGraph filter's script, qtype_geogebra's worksheet XML. STACK, filter, qtype_geogebra
  • tldraw syncs records keyed by id and exports SVG through each shape's toSvg; Excalidraw merges per element by version and draws its SVG from the same shape cache as its canvas. tldraw export, Excalidraw renderers

The common pattern, which this plan follows: graphs are recipes of objects naming their points; live co-editing merges one object at a time; SVG comes from the product's own drawing code.
