# Make a quiz: the layout model with int8 convolutions (2026-11-10)

The layout service runs PP-DocLayout_plus-L as a float ONNX model, at about 1
CPU-second a page ([layout models](2026-11-04-layout-models.md)). This run looked
for a cheaper way to run the same weights on the ingest host, with no
retraining. Epo agreed on 2026-11-10 to build the result into the service,
after the check on fresh pages below.

## Answers

- **Quantise the convolutions to int8 and nothing else.** On the ingest host a
  page costs 528 CPU-ms against 970, which is 1.84x the pages per CPU-second.
  The file goes from 130 MB to 58 MB and peak memory from 544 MB to 425 MB.
- **The figures score the same.** The gold crops score exactly as the float
  model's. On 331 fresh pages every one of the 150 figure boxes production
  would use came back, with none gone and none new; on the 196 mixed pages the
  figure boxes changed on one page. These are the Mac's build of the int8
  model; the host's build, which ships, gives the same regions as it on 99.9%.
- **One thread an inference is the cheapest.** Two threads cost the same CPU a
  page and four cost 11% more, so more threads only shorten one page's wait.
- **Quantising more breaks the model.** See [Tried and dropped](#tried-and-dropped).

## How the int8 model is built

`layout/quantise.py` runs in a stage of the service's image build
(`layout/Dockerfile`) on the float export the Dockerfile pins by revision and
SHA-256 (`77afb2ca…07ff0e`):

1. `quant_pre_process` with symbolic shape inference off: onnxruntime's basic
   optimisation (constant folding) and ONNX shape inference.
2. `quantize_static` in QDQ format on `Conv` nodes only (all 110), weights int8
   per channel, activations uint8, MinMax ranges read from
   `layout/calibration-ranges.json`. No calibration page is read, so this step
   needs no data and no network; the build's package install and model download
   do. The script then fails unless every convolution reads int8 data and
   weights.

The build stage installs onnx 1.23.2, onnxruntime 1.31.1 and numpy 2.2.6
(`layout/requirements-quantise.txt`); the runtime image takes only the int8
model and keeps its own packages. The service's code is unchanged: the int8
model has the float model's inputs and outputs.

**Calibration.** MinMax over 97 pages: 58 from 30 web PDFs, 30 from library
books and 9 from fixture PDFs, rendered as production renders a page (long
side 1,568 px, JPEG quality 80). The ranges were collected on the Mac for
1,111 tensors. Recalibrating on the host's CPU from the same JPEGs gave ranges
within 0.002% of the Mac's on the 1,110 finite ones. The committed file keeps
the 185 tensors the convolutions read, their inputs and outputs; built from it,
the model is byte for byte the one built from the whole file.

## What ran

- **Timing.** The ingest host (AMD EPYC 9645), onnxruntime 1.31.1, 60 mixed
  pages, one page a call, a fresh process for each model and thread count. CPU
  time is the process's, all threads, for the model call alone.
- **Gold figures.** The 59 gold pages of the layout models report, scored by
  `scripts/layout_score.py` with the crop rule and its 1% pad.
- **Agreement with the float model.** A region is reproduced when the other
  model has one with the same label, an IoU of 0.8 or more and a score of 0.5
  or more. Figure boxes are what production's `layout.figure_boxes` keeps, at
  0.5% of the page or more.
- **Page sets.** 196 mixed pages (web PDFs, fixtures, library books), and 331
  fresh pages from 72 PDFs that are in neither the calibration set nor any
  earlier test set.

The pages and the raw records stayed on the Mac under the gitignored
`bench/parsers/reports/local/`, out of this public repository, with the local
scripts that made these numbers. The same steps are in `scripts/`:
`layout_detect.py` times a model and records its regions, `layout_score.py`
scores the gold figures and `layout_agree.py` compares two models' regions
([Reproduce](#reproduce)). Gold scoring and agreement ran on the Mac's build of
the int8 model, timing on the host's.

## Results

**Cost, ingest host, one thread:**

| | Float | int8 convolutions |
|---|---|---|
| CPU a page | 970 ms | 528 ms |
| Model file | 130 MB | 58 MB |
| Peak RSS | 544 MB | 425 MB |

**Gold figures, crop rule with a 1% pad.** Both models score the same:

| Pages | Found | Whole | Tight | Both |
|---|---|---|---|---|
| Scans (14 figures) | 14 | 14 | 14 | 14 |
| Born-digital (26 figures) | 26 | 24 | 23 | 21 |

**Agreement with the float model:**

| Pages | Float regions the int8 model reproduces | int8 regions the float model has | Figure boxes |
|---|---|---|---|
| 196 mixed | 98.7% | 99.0% | changed on one page |
| 331 fresh | 98.9% | 99.2% | all 150 reproduced, none gone, none new |

On the fresh pages the int8 model reproduced 99 of 99 tables and 96% of
formulas.

## Tried and dropped

- **The decoder's MatMuls in int8.** About a fifth of the regions are lost.
- **Query selection or post-processing in int8.** No detections at all.
- **No gain:** batching pages, flushing denormals to zero, a saved optimised
  graph, and OpenVINO in place of onnxruntime.
- **Dynamic int8 on the MatMuls.** 862 CPU-ms a page at one thread and 963 at
  two, 11% and 3% under the float model: too little to carry a second change.

## Limits

- **Calibration and the mixed set overlap.** The 97 calibration pages share
  documents with the 196-page set. The 331-page set shares none.
- **Gold scoring ran on the Mac's build.** The int8 file's bytes differ between
  build machines: the first step's output already differs between the Mac and
  the host. The host's build reproduced the Mac build's detections on 99.9% of
  regions; it was timed, not gold-scored.
- **The shipped script and image were each checked once.** On the Mac the
  script gives the Mac build byte for byte (SHA-256 `72d9d88e…40519a`) and the
  same 1,573 regions on the 59 gold pages. The image was built once on the
  ingest host: its model is the host build that was timed (`9f8d9c6d…083304`),
  and the runtime image's package list holds no quantisation package. It is
  349 MB against the float image's 421 MB, the difference being the model.
  Run as the service with one thread and no network, four mixed pages took 500
  to 635 ms of inference each in 380 MiB; three pages' regions matched the Mac
  build's and the fourth's did on 55 of 59.
- **One process, one page at a time.** Nothing here ran under load or beside a
  busy parser. The
  [capacity test](2026-11-04-layout-capacity.md)'s pages a second and its
  memory limit are the float model's.
- **Measured on CPUs with VNNI only.** The Mac is ARM and the host's EPYC 9645
  has AVX-512 VNNI. On x86 without VNNI, onnxruntime's uint8 by int8
  convolutions can saturate, so a move to such a CPU needs the gold check
  again.
- **Formulas agree least**, at 96%. Make a quiz reads `image`, `chart`, `text`
  and `figure_title` regions (`retrieval/layout.py`), and no formula region.

## Reproduce

With the versions in `layout/requirements-quantise.txt` and the pinned float
export:

```sh
python layout/quantise.py inference.onnx int8.onnx
```

With the int8 file as `inference.onnx` in a folder beside the export's
`inference.yml`, and pages rendered by `layout_detect.py render`:

```sh
python bench/extraction/scripts/layout_detect.py detect --backend pp-onnx \
    --model PP-DocLayout_plus-L --path <int8 folder> --pages <pages> --out int8.json
python bench/extraction/scripts/layout_score.py int8.json
python bench/extraction/scripts/layout_agree.py float.json int8.json
```
