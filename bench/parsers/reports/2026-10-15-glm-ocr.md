# GLM-5.3-Flash as the OCR stage

2026-10-15. Could GLM-5.3-Flash on Relace replace the parser's local RapidOCR
stage, and how much load does Relace take before requests fail?
[The v14 stress run](2026-10-15-parser-v14-stress.md) found the one OCR process
at 3.6 cores and about 27 pages a minute: the parser's throughput limit, with
no room on the 8-CPU host for a second one. Runner:
[`scripts/ocr_glm.py`](../scripts/ocr_glm.py), run on the ingest host inside
the parser image, so calls leave from where production would make them.

## Decision

None yet. Findings for the developer:

- **Quality: GLM matches or beats RapidOCR on every group and adds the
  structure RapidOCR never had.** Its token recall is equal or higher
  everywhere: 0.943 over the 46 scored pages, against 0.914 for RapidOCR.
  It returns:
  - headings and Markdown tables;
  - Unicode or LaTeX mathematics (`C₁`, `ℤ⁺`, `⌈(n−1)/2⌉`);
  - descriptions of figures and diagrams, including labels the text layer
    never had.

  It loses the per-line boxes, which were the citation anchors on scanned
  pages; the developer accepted that.
- **Speed and cost per page.** 1,280 px renders read as well as 2,048 px ones
  with 60% fewer input tokens: about 1,650 input and 460 output tokens a page.
  - Median 6.9 s a page, p90 15 s.
  - $0.0003 a page, so $0.30 per 1,000 pages.
  - That is about 0.48 credits a page at the catalog rates, against the
    1.0 credit an OCR page is billed today.
  - Reasoning at `low` used 0 tokens on every call.
- **Capacity on one key:**
  - Up to 64 requests in flight, no failures, about 190 pages a minute.
  - At 128, 9% were shed and about 470 pages a minute completed.
  - Local RapidOCR does 27 pages a minute.
- **The limit is Relace's per-server load shedding, not a per-key rate.**
  - When a server already serves 32 or more requests, it answers new
    sessions with `429` and asks for a retry after 2 s ("new sessions are
    shed so a pooled peer takes them; a continued (cached) session is
    served").
  - An OCR request is always a new session. Chat turns that continue a
    cached conversation are protected; a chat's first turn is not.
  - The shed 429 arrives after about 8 s, not at once.
  - The per-minute limit never triggered: 384 requests started within one
    minute.
- **A second key on a different account adds no serving capacity.** The two
  accounts share one pool of servers:
  - alone at 128 in flight, the chat key shed 22 of 256 requests and the
    ingest key 3 of 256;
  - together at 256 in flight, they shed 131 of 512 (26%);
  - completed throughput rose only from about 465 to 580 pages a minute.

  The second key still separates usage and per-key rate budgets, so it is
  worth keeping. It does not justify running ingest outside the capacity
  gate.
- **One degenerate output in 717 calls.** In the two-key run, one request
  ran to the 8,192-token cap in 119 s. A normal page is about 460 output
  tokens.
- **Fidelity notes:**
  - A page repeating one sentence 29 times came back as the sentence once,
    plus a note saying it repeats.
  - One textbook page put its "Questions to consider" sidebar before the
    body text.
  - A degraded limb diagram's digit labels were assigned per animal, and the
    totals match the page.
  - No text that wasn't on the page was found in the pages read by hand.

## Setup

- `RELACE_API_KEY` from `deploy/.env.uat` (the chat key), plus
  `RELACE_INGEST_API_KEY` (a second account) for the two-key run. Both were
  written to a root-only file on the host and deleted after each run.
- Model `z-ai/glm-5.3-flash` at `reasoning_effort: low`, temperature 0,
  `max_tokens` 8,192, no retries, 180 s client timeout.
- The developer's prompt was sent as the system message: "Caption this page
  and extract all the visible text, formulas, tables and images. Keep text
  identical. Do not add any information not visible on the page. The result
  is directly consumed through a RAG pipeline." The page went in the user turn.
  - **A system message is required.** Without one, 46 of 55 requests got
    `400` "This deployment does not accept image input without conversation
    context (a system prompt, tools, or prior messages)."
- Pages are grey JPEG renders (quality 80) at 1,280 or 2,048 px long edge.
- The RapidOCR arm is `odl.ocr.page_blocks` in the parser image (`02f83a57`),
  4 CPUs, as in production.

## Capacity

Each level sends 2 × N page requests (1,280 px) with N in flight, cycling
through the 47 non-degraded pages. Levels ran back to back.

| Key | In flight | OK | 429 | Median | p95 | Max | Pages/min |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| chat | 8 | 16/16 | 0 | 7.8 s | 21.8 s | 21.8 s | 33 |
| chat | 16 | 32/32 | 0 | 9.2 s | 17.2 s | 22.8 s | 84 |
| chat | 32 | 64/64 | 0 | 8.0 s | 15.7 s | 20.5 s | 137 |
| chat | 64 | 128/128 | 0 | 10.7 s | 26.6 s | 32.5 s | 189 |
| chat | 128 | 234/256 | 22 | 10.6 s | 24.5 s | 36.6 s | 470 |
| ingest | 32 | 64/64 | 0 | 9.2 s | 18.0 s | 24.3 s | 119 |
| ingest | 128 | 253/256 | 3 | 10.9 s | 26.6 s | 91.5 s | 460 |
| both at once | 128 + 128 | 381/512 | 131 | 13.8 / 12.7 s | 30.4 / 29.2 s | 119 s | 580 |

- "Pages/min" for the 128 levels counts completions until 90% are done, so a
  single slow tail request doesn't set the figure. Every other level
  finished within its wall time.
- **Two kinds of 429 in the two-key run:**
  - 111 were the shed message, "Serving 40 requests (threshold 32)";
  - 20 were bare, with no body and no `Retry-After` (14 on the chat key,
    6 on the ingest key).
- The chat key's run at 128 began with 384 requests started in the previous
  minute and saw only shedding. The 700–800 RPM budget measured on
  2026-09-26 was never reached.

## What this means for an OCR queue

- **Use a separate gate for OCR, sized below the shedding point.**
  - With nothing else running, 64 in flight never failed.
  - Chat shares the pool, even on another account.
  - 16–32 OCR calls in flight would give 85–135 pages a minute: 3 to 5
    times today's local OCR.
- **Retry shed 429s.** They tell the client to retry after 2 s, and ingest
  retries are allowed.
- **Lower `max_tokens`.** A page needs about 460 output tokens. A cap of
  about 2,000 would stop a degenerate loop in about 30 s instead of two
  minutes.
- **Freed resources if OCR leaves the parser:** about 3.6 cores and
  1–1.4 GiB per busy OCR process (v14 stress run).

## Not covered

- Real phone photos, handwriting, and scans with tables. The scored set's
  scans are clean renders, and the two real scans are synthetic test pages.
- Long-run behaviour: one ~15-minute window per test, from the ingest host.
- Chat traffic during the OCR ramps. Chat's first turns are new sessions too,
  so OCR load can shed them.

## Reproduction

Pages, outputs, scores, ramp logs and scripts are in the ignored
`reports/local/2026-10-15-glm-ocr/`. On the host, in
`/opt/capy-ocr-glm-20261015`, inside the parser image with
`PYTHONPATH=/app/parser`:

```sh
python ocr_glm.py prepare --manifest pages.json --out run
python ocr_glm.py rapid --out run
python ocr_glm.py glm --out run --edge 1280 --concurrency 8
python ocr_glm.py score --out run
python ocr_glm.py ramp --out run --edge 1280 --levels 8 16 32 64 128
python ocr_glm.py ramp --out run --edge 1280 --levels 128 --key-env RELACE_INGEST_API_KEY --tag=-b
```

About 1,550 GLM calls in all (46 of them refused with 400 before the system-message fix), under $0.40.
