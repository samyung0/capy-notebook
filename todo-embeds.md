# Embeds: catalog, drift and open work

From the 2026-10-13 survey of how rich blocks (quiz, flashcards, mermaid,
chart, plot, graph, html-embed) move between chat, notes, standalone
materials, the collaboration server and agent prompts. Nothing below is
decided except where marked; current behaviour lives in
`openwiki/frontend/plate-editor.md`, `openwiki/question-bank.md` and
`openwiki/agentic-retrieval.md`.

Landed with this file: a live quiz room keeps plot blocks (they used to vanish
from the projection, so an agent's `add_question_media` plot never reached
learners; `plot.json` joins the shared question fixtures), the materials skill
no longer offers graph media (nor do the `contract.py` and `tools.py`
comments), and `/generate` no longer offers a chart `unit`.

## Where things stand

Each kind has a different name per layer, and the lifecycle code follows the
storage class rather than the kind:

| Kind | Plate node | Note fence | Chat (OpenUI) | Material kinds | Class |
| --- | --- | --- | --- | --- | --- |
| chart | `chart` | ```` ```chart ```` (JSON) | `Chart` | – | inline value |
| plot | `plot` | ```` ```plot ```` (JSON) | `Plot` | – | inline value |
| graph | `graph` | ```` ```graph ```` (JSON) | – | – | inline value |
| html-embed | `html_embed` | ```` ```html-embed ```` (YAML) | `Interactive` | – | inline value |
| mermaid | `mermaid` (+ caption) | ```` ```mermaid ```` (source) | `Diagram` | mindmap, diagram | live source (Y.Text) |
| quiz | `material_ref` (`refKind: quiz`) | ```` ```quiz ```` (YAML) | – | quiz | item reference |
| flashcards | `material_ref` (`refKind: flashcards`) | ```` ```flashcards ```` (YAML) | – | flashcards | item reference |

- **Inline value**: an attribute on the node, replaced whole; no row, no room
  of its own.
- **Live source**: a Y.Text `source`, so concurrent typing merges.
- **Item reference**: a child material row with its own rooms; Go owns access,
  trash, clone, share, assets and quota for it.

Chart, plot and graph are also question blocks (one schema for quizzes, notes
and chat). Plot has no editor anywhere (Epo 2026-10-13: not now): agents write
it, the question dialog and notes show it view-only, and users can remove it.

The fence parser is already single: the collaboration server runs the editor's
own `markdownConvert.ts` in V8. Everything else repeats the kind list by hand:
about 35 lists in `src/`, 15 in `collaboration-rs`, 30 across Go and Python.
The chart/plot schema exists five times: zod (`questions/validation.ts`), Go
`ValidateBlock`, Rust `notes/src/questions.rs`, Python `_chart_problems`, and
the `mediaBlocks` JSON Schema in the agent contract.

## Proposal: an embed catalog checked by every layer

The agent tool catalog worked because a tool lives in one layer with one
schema. An embed crosses five layers whose code differs for good reasons
(chat streams partial programs, Plate needs void nodes and selection fixes,
share pages need islands), so the counterpart is a catalog each layer is
**tested against**, not one each layer runs from.

1. **`embeds.json`, generated by `pnpm gen:openapi` from Go** (next to
   `agenttools`, which already owns the agent contract and `mediaBlocks`; the
   same freshness test and version handshake). One entry per kind: its name in
   every layer (Plate type, fence language and body format, OpenUI component,
   material kinds), storage class, data schema (JSON Schema; `mediaBlocks`
   moves here), limits, asset fields, which surfaces render it, who edits it
   where (user editor per surface, agent commands), whether it is allowed in
   questions, and its agent-facing text. A TS copy is generated beside
   `src/api/limits.generated.ts`.
2. **Agent text from the catalog.** `Formats.note` and the OpenUI
   descriptions of `Chart`, `Plot`, `Diagram` and `Interactive` quote each
   kind's text, so the html-embed rules exist once (today
   `agenttools.go:463` and `chat/schema.ts:328`). Python kind lists
   (`questions.py` `_MEDIA`, the skills text) read the catalog.
3. **One set-equality test per language** comparing its hand-written lists
   with the catalog: TS (`CUSTOM_BLOCK_LANGS`, the markdown serialize rules,
   `staticPlugins`, `document.ts` `CUSTOM_TYPES`, chat's Diagram/Chart to fence
   mapping), Rust (`material.rs` `validate_node`, `limits.rs` `OWN_KEYS`, quiz
   `BLOCK_TYPES` against question media, `edit.rs` inspect), Go
   (`validateNode`, `ValidateKind`). These would have caught every drift item
   below, the plot-in-quiz gap included.
4. **Shared valid/invalid fixtures per kind** that zod, Go, Rust and Python
   must all agree on, extending `server/internal/questions/testdata` (already
   read by the Rust item tests and parity corpus). Validators are not generated
   from JSON Schema: their error messages are tuned for agents and users.
5. **Embed limits in the generated limits** (`HTML_EMBED_MAX_BYTES`/`COUNT`
   carry a "keep in sync" comment in `document.ts:107`), with a Rust output
   added (`notes/src/questions.rs` constants are hand-copied today).
6. **`openwiki/embeds.md`**: the table above plus the catalog's fields, listed
   in AGENTS.md's wiki table.

Not centralized: renderers and editors (they already share `Mermaid.tsx`,
`CategoryChart`/`PlotChart` and `HtmlEmbed.tsx`), lifecycle code (per storage
class, in Go), and no cross-language plugin registry or universal embed node.

**Order**: the drift list first, then the catalog with its tests (they surface
whatever drift is left), then the agent text.

**Open for Epo**: Go as the catalog's source; whether to unify names while
there is no legacy data (`html-embed` / `html_embed` / `Interactive`,
`Diagram` / `mermaid`, mindmap and diagram both being one mermaid node).

## Drift found 2026-10-13

Fixed with the Go and browser catalog tests (see Progress): the missing
`chart`/`plot`/`graph` markdown serialize rules, chat's `ScatterChart` stub,
`RESIZABLE_TYPES`' `diagram` and `mindmap`, list cards labelling mindmaps and
diagrams "Note", `blocks.ts`' unused fence writers, `MermaidBlockLabel.ts`,
Go's `image`, `toggle` and `details` leftovers and Go's `pending` on a
resolved reference. Fixed in the Rust round: `inspect_document` prints a
plot's `block`, Rust keeps one media list (`material::MEDIA_TYPES`), and
`pending` is refused on any reference in Go and Rust alike. Open:

- **Footnotes** (decided 2026-10-14: text on import). A reference is its
  label in superscript, a definition its paragraphs led by that label; the
  catalog no longer lists `footnoteReference`/`footnoteDefinition`.
- **Card images in fences** (decided 2026-10-14: dropped). No fence ever
  carries one (agents write fronts and backs, export flattens a set to text,
  Copy moves the block), and a hand-written one names another document's
  asset. Agent writes, paste and import read a fence with one parser,
  `parseEmbeddedFence` (merged 2026-10-14).
- The notes markdown corpus (`collaboration-rs/crates/notes/tests/corpus`) has
  no chart, plot or graph fence; it is a frozen Node oracle, so new cases go in
  by hand.
- The note format never mentions a ```` ```graph ```` fence while the
  converter accepts one (paste and export round trips); intended, but the
  catalog should say so.
- `openui.py` keeps its own `_SKIPPED_PROPS` (TS chart kinds are one
  `CHART_KINDS` read from the catalog since 2026-10-14).

## Decisions (Epo, 2026-10-13)

1. **Unknown kinds are refused** by every layer: the store, room admission and
   every validator refuse a block type the catalog does not list; readers that
   meet one fail loudly in tests instead of dropping it.
2. **The HTML embed source stays replace-whole** (the save-style dialog); no
   live shared text for it. Revisit if co-editing HTML becomes common.
3. **Names are unified now, one word per kind in each layer's casing.**
   `mermaid` everywhere (chat's `Diagram` becomes `Mermaid`); `html_embed` /
   ```` ```html-embed ```` / `HtmlEmbed` (chat's `Interactive` becomes
   `HtmlEmbed`); chart, plot and graph unchanged; mindmap and diagram stay
   material kinds (user-facing), both holding one mermaid node. Plate types and
   fences already follow this rule, so saved notes do not change: the rename is
   chat's components, the agent text and contract (a version bump; Go and the
   pipeline deploy together). Done with the catalog, after the drift fixes.
4. **The catalog is generated from Go** (next to `agenttools`, through
   `pnpm gen:openapi`), with a generated TS copy and a generated Rust file, so
   Rust stops hand-copying limits.
5. **A stored document with a block nothing recognizes stays readable, and
   editing it is refused**: View renders an "unsupported block" placeholder in
   its place and the rest as usual; Edit refuses with a clear message until the
   document is fixed. No compatibility code. After the rename, old UAT chat
   answers that use `Interactive` or `Diagram` are the documents to watch.

## Feedback from the Rust collaboration session (2026-10-13)

The live layer (Rust server, live items, live View, live Mermaid) holds
per-kind knowledge that point 3's test list does not name. Both Rust drift
items above are confirmed (`edit.rs:189` vs `material.rs:24`; plot missing
from inspect at `edit.rs:1375`). Add these catalog fields and test them:

- **Live (shared-text) fields.** Only `mermaid.source` merges character by
  character, and that is hard-coded in six places: `notes/src/plate.rs:284`
  (`SHARED_TEXT_KEY`), `slate_yjs.rs:244`, `limits.rs:500,519`,
  `bound.rs:331`, `patches/@slate-yjs__core@1.0.2.patch`, `liveMermaid.ts`.
  Missing one breaks typing subtly.
- **Required and forbidden keys.** `limits.rs:279` `OWN_KEYS` drives room
  admission; Go `validateNode` and Rust `material.rs:434` drive the store. If
  admission and store disagree, an accepted edit is refused at store and
  co-editors lose unsaved work (fixed twice this round). Forbidden keys too:
  `pending` on `material_ref` is refused in `limits.rs:626`,
  `material.rs:344,365`, Go `isPendingRef`, `0080_cutover_reset.sql`,
  `pendingRefs.ts`. Go's `validateMaterialRef` still accepts `pending` with an
  empty id (only the note check refuses it); Rust refuses it on any ref.
- **Placement.** `material_ref` top-level only and only in notes; mindmap and
  diagram materials need a mermaid block (`material.rs:483-607`); which
  material kinds are items (`items/src/lib.rs:44` `Kind::of_material`); the
  `refKind` sets (Rust, Go `refKinds`, TS `useNoteFooter.ts` `embedKey`,
  `AppEmbed.tsx`).
- **Asset fields.** Top-level `assetId`, quiz_question and flashcard images,
  question image blocks: walked by the server's children pass
  (`server/src/children.rs`), Go's asset prune and clone rewrite
  (`document.go:1327-1390`), and the two Rust `MEDIA_TYPES`. Untested today.
- **Question blocks in live quiz rooms.** Rust `items/src/quiz.rs` `BLOCK_TYPES`
  / `read_block` / `block_shape` and TS `liveQuiz.ts` `readBlock` /
  `writeBlockFields`. The TS reader drops unknown kinds (`default: null`), the
  same failure as the plot gap.
- **Error messages.** Rust says "chart and graph embeds" where Go says "chart,
  plot and graph". Agents read these: fixtures should compare a stable error
  code plus the agent-facing text the catalog holds.
- **Live View** exists only for notes (`CenterContent.tsx:550`); mindmap and
  diagram Views stay static. Intended for now; the catalog's surfaces field
  should say so.

These drift items were fixed in the Rust round (see Drift above).

## Next: every embed live, indexed and in effects (Epo, 2026-10-17)

Asked for as one round in its own session: all embeds unified across chat
(OpenUI) and Plate, and every embed with live editing, index text and note
effects. That means:

- live edits for charts and graphs (today an inline value replaced whole, so
  two editors' changes do not merge) and a plot editor UI (plot had none:
  "not now", 2026-10-13);
- one component set for chat and notes per kind;
- each kind's text in the note's index text, so the agent sees its changes
  through note effects.

Record the scope in `human/frontend/plate-editor.md` when the round starts.

What an embed contributes to index text today (Go's `ExtractIndexText`,
`server/internal/materialdoc/document.go`, used by `note_index.go` for
`rag_material_contents`):

| Element | Index text |
| --- | --- |
| chart, plot | `block.title` only (no data) |
| graph | `block.description` only |
| mermaid (source and caption) | none |
| html_embed | none |
| material_ref (quiz, flashcards) | none; only `kind='note'` materials are indexed, so the quizzes and flashcard sets never are |
| img, audio, video, equation, inline_equation, toc, hr | none (image captions too) |

Note effects (decided 2026-10-17, `human/agentic-retrieval.md`: the per-turn
read against the per-block index text the last index job recorded, aligned by
element id, one Rust index-text extraction shared with Go, reindexing on a
token threshold) cover an embed exactly where its index text does. A changed
Mermaid source, chart data or HTML embed is invisible to the agent until the
index text holds it, and holding it also makes it searchable.

Proposed catalog change for this round: each element in
`server/internal/embeds` declares what it contributes to index text (nothing,
its children's text, or named fields such as `block.title`). Go's
`ExtractIndexText` and the coming Rust extraction both read it, and each
layer's catalog test fails on an element without a rule. Today the rule is a
hand-written list (`indexSkipped` plus the chart, plot and graph case), and an
element missing from it silently indexes its children's text.

Open questions for that session:

- How each kind's live state is shaped: shared Y types per field, as
  `mermaid.source` is today, or whole-value replacement with merge rules.
  Either way it is a client protocol decision (`CLIENT_PROTOCOL`,
  `MIN_MATERIAL`).
- What text each kind indexes: a chart's series names and labels, a Mermaid
  source's node labels, an HTML embed's caption or visible text.
- Whether quiz and flashcard items get index text of their own.

The note effects themselves (pending effects plus the token threshold) are
queued in the effects round (`todo-office-effects.md` and the decision
above), so the two rounds share the Rust index-text extraction.
